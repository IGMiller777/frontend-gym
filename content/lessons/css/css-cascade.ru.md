## О чём урок

«Почему не применяется мой стиль» почти всегда объясняется каскадом: какое объявление побеждает, когда к элементу подходит несколько правил. Здесь порядок каскада, специфичность (и почему её нельзя считать как 1000/100/10/1), `!important`, каскадные слои `@layer`, `@scope` и наследование. Специфичность в примерах считает библиотека `@bramus/specificity`, она реализует алгоритм из спецификации Selectors.

## Порядок каскада

Когда несколько объявлений задают одно свойство одному элементу, браузер сравнивает их по шагам и останавливается на первом различии:

1. **Источник и важность**: стили браузера, пользователя и автора; объявления с `!important` идут отдельной группой, где порядок источников обратный.
2. **Контекст**: стили внутри Shadow DOM против стилей страницы.
3. **Атрибут `style`** побеждает правила из таблиц стилей.
4. **Каскадные слои** (`@layer`): более поздний слой побеждает более ранний; стили вне слоёв побеждают все слои.
5. **Специфичность** селектора.
6. **Близость** `@scope`: ближе к корню области побеждает.
7. **Порядок**: при прочих равных побеждает объявление, которое идёт позже.

Важно: слои сравниваются **раньше** специфичности. Правило `.btn` в позднем слое победит `#app .btn` в раннем.

## Специфичность это три числа

Специфичность записывают как тройку (A, B, C):

- **A**: селекторы `#id`;
- **B**: классы `.x`, атрибуты `[type]`, псевдоклассы `:hover`;
- **C**: теги `div` и псевдоэлементы `::before`.

Тройки сравнивают слева направо, как версии программ, а не складывают. Поэтому сколько угодно классов не перебьют один `id`.

```js run
import Specificity from "@bramus/specificity"
const selectors = ["#nav a", ".btn.btn-primary", "ul li a:hover", ".a.b.c.d.e.f.g.h.i.j.k", ":where(#app .card) p", ":is(#a, .b) span", "a:not(.x, #y)", "div:has(> img)"]
for (const s of selectors) console.log(s.padEnd(24), Specificity.calculate(s)[0].toString())
const elevenClasses = Specificity.calculate(".a.b.c.d.e.f.g.h.i.j.k")[0]
const oneId = Specificity.calculate("#x")[0]
console.log("11 classes vs 1 id:", Specificity.compare(elevenClasses, oneId) < 0 ? "id wins" : "classes win")
```

```output
#nav a                   (1,0,1)
.btn.btn-primary         (0,2,0)
ul li a:hover            (0,1,3)
.a.b.c.d.e.f.g.h.i.j.k   (0,11,0)
:where(#app .card) p     (0,0,1)
:is(#a, .b) span         (1,0,1)
a:not(.x, #y)            (1,0,1)
div:has(> img)           (0,0,2)
11 classes vs 1 id: id wins
```

Правила для псевдоклассов-функций:

- `:where(...)` всегда даёт **ноль**: удобно для базовых стилей, которые легко переопределить;
- `:is(...)`, `:not(...)` и `:has(...)` берут специфичность **самого сильного** аргумента;
- универсальный селектор `*` и комбинаторы (` `, `>`, `+`, `~`) не добавляют ничего.

## !important

`!important` переносит объявление в отдельную группу, которая побеждает **любые** обычные объявления, независимо от специфичности. Между двумя `!important` снова решают слои, специфичность и порядок. У важных объявлений порядок слоёв обратный: `!important` в раннем слое сильнее, чем в позднем. Это сделано, чтобы базовый слой мог защитить, например, `[hidden] { display: none !important }`.

Использовать `!important` в своём коде стоит только для таких защитных правил и для утилит, которые должны побеждать всегда. Борьба специфичностью через `!important` заканчивается войной важностей.

## Каскадные слои

`@layer` даёт явный порядок групп стилей, не зависящий от специфичности и от порядка подключения файлов:

```css
@layer reset, base, components, utilities;

@layer base {
  a { color: var(--link); }
}
@layer components {
  .card a { color: inherit; }
}
@layer utilities {
  .text-red { color: red; }
}
```

Объявленный первой строкой порядок фиксирует старшинство: утилита `.text-red` победит `.card a` из слоя компонентов, хотя у неё меньше специфичность. Стили сторонних библиотек кладут в ранний слой (`@import url(lib.css) layer(vendor)`), и любой свой стиль их перебивает. Tailwind v4 сам раскладывает свои стили по слоям `theme`, `base`, `components`, `utilities`.

## @scope

`@scope (.card) to (.card-content) { … }` применяет стили только внутри `.card` и не дальше `.card-content`. Если подходят две области, побеждает ближайшая к элементу. Это нативная замена соглашениям об именах вроде BEM и части CSS Modules; поддерживается всеми основными браузерами.

## Наследование

Часть свойств наследуется от родителя: `color`, `font-*`, `line-height`, `visibility`, `cursor`, а также CSS-переменные. Другие нет: `margin`, `padding`, `border`, `background`, `width`. Управлять этим помогают ключевые слова:

| Значение | Что делает |
|---|---|
| `inherit` | взять значение родителя |
| `initial` | начальное значение из спецификации (`display: initial` это `inline`) |
| `unset` | `inherit` для наследуемых, `initial` для остальных |
| `revert` | вернуться к стилю браузера |
| `revert-layer` | вернуться к значению из предыдущего слоя |

## Главное

- Каскад: источник и важность, контекст, `style`, слои, специфичность, близость `@scope`, порядок.
- Специфичность это тройка (id, класс, тег), её сравнивают, а не складывают; 11 классов проигрывают одному `id`.
- `:where()` даёт ноль, `:is()`, `:not()`, `:has()` берут самый сильный аргумент.
- `!important` побеждает любые обычные объявления; у важных порядок слоёв обратный.
- `@layer` задаёт порядок групп сильнее специфичности; стили вне слоёв сильнее всех слоёв.
