## О чём урок

JavaScript в браузере выполняется в одном потоке: пока работает ваш код, страница не реагирует на клики и не перерисовывается. Чтобы ждать сеть, таймеры и события, не блокируя этот поток, браузер использует **цикл событий** (event loop). Почти все задачи «что выведет код» проверяют именно его.

Примеры урока выполняются как ES-модули в Node.js. Порядок промисов и таймеров там такой же, как в браузере; то, чего в Node.js нет (отрисовка, `requestAnimationFrame`), показано обычным кодом без запуска.

## Стек вызовов

Стек вызовов (call stack) хранит функции, которые выполняются прямо сейчас. Вызов функции кладёт кадр на вершину, возврат снимает его. Пока стек не пуст, движок занят, и ничего другого не происходит: ни колбэки таймеров, ни обработчики кликов, ни отрисовка.

Отсюда главное правило: асинхронный колбэк никогда не прерывает работающий код. Он ждёт, пока стек опустеет.

## Две очереди

Колбэки ждут своей очереди в двух местах.

| Очередь | Что туда попадает |
|---|---|
| **Задачи** (tasks, их ещё называют макрозадачами) | колбэки `setTimeout` и `setInterval`, события (`click`, `input`), сообщения `postMessage`, ответы сети, сам запуск `<script>` |
| **Микрозадачи** (microtasks) | реакции промисов (`then`, `catch`, `finally`), продолжение после `await`, `queueMicrotask`, колбэки `MutationObserver` |

Один виток цикла событий по спецификации HTML выглядит так:

1. Взять **одну** задачу из очереди задач и выполнить её до конца.
2. Выполнить **все** микрозадачи, включая те, что добавились по ходу.
3. Если пора обновить экран (обычно раз в кадр, около 16,7 мс при 60 Гц), выполнить колбэки `requestAnimationFrame`, пересчитать стили, раскладку и отрисовать кадр.
4. Если до следующего кадра осталось время, выполнить колбэки `requestIdleCallback`.

Запуск скрипта тоже задача. Поэтому после синхронного кода сначала разбираются все микрозадачи, и только потом выполняется первый таймер.

```js run
console.log("script start")
setTimeout(() => console.log("timeout"), 0)
Promise.resolve().then(() => console.log("promise"))
queueMicrotask(() => console.log("microtask"))
console.log("script end")
```

```output
script start
script end
promise
microtask
timeout
```

## Микрозадачи до пустой очереди

Очередь микрозадач разбирается целиком, даже если микрозадачи добавляют новые микрозадачи. Таймер ждёт.

```js run
setTimeout(() => console.log("timeout"), 0)
let n = 0
function tick() {
  n++
  if (n < 3) queueMicrotask(tick)
  else console.log("microtasks done:", n)
}
queueMicrotask(tick)
```

```output
microtasks done: 3
timeout
```

Если микрозадачи будут порождать друг друга бесконечно, очередь никогда не опустеет: не выполнятся ни таймеры, ни клики, ни отрисовка, и вкладка зависнет. Бесконечная цепочка `setTimeout` такого не делает, потому что между задачами браузер успевает рисовать.

## После каждой задачи

Микрозадачи разбираются не только после скрипта, а после **каждой** задачи. Промис, созданный в колбэке таймера, выполнится раньше следующего таймера, даже если тот уже в очереди.

```js run
setTimeout(() => {
  console.log("timeout 1")
  Promise.resolve().then(() => console.log("promise in timeout 1"))
}, 0)
setTimeout(() => console.log("timeout 2"), 0)
```

```output
timeout 1
promise in timeout 1
timeout 2
```

## Отрисовка и requestAnimationFrame

Браузер рисует кадр между задачами, а не во время них. Если обработчик клика меняет DOM пять раз подряд, пользователь увидит только итог. Долгая задача (дольше 50 мс её называют long task) задерживает следующий кадр и реакцию на ввод, это напрямую ухудшает метрику INP.

`requestAnimationFrame(cb)` вызывает `cb` прямо перед отрисовкой следующего кадра. Это правильное место для анимаций на JavaScript и для чтения размеров перед изменением DOM.

```js
setTimeout(() => console.log("timeout"), 0)
requestAnimationFrame(() => console.log("frame"))
// Порядок не гарантирован: обычно "timeout" раньше,
// но если кадр как раз должен рисоваться, первым может быть "frame".
```

Задачи «что выведет код», где `setTimeout` соревнуется с `requestAnimationFrame`, не имеют единственного верного ответа. Хороший ответ на собеседовании это объяснить, от чего зависит порядок.

## Node.js отличается

В Node.js свой цикл событий из библиотеки libuv, с фазами (таймеры, ввод-вывод, `setImmediate`, закрытие). Микрозадачи работают как в браузере, но есть ещё очередь `process.nextTick`, которая разбирается раньше промисов. Порядок `setTimeout(fn, 0)` и `setImmediate(fn)` в главном модуле не гарантирован; внутри колбэка ввода-вывода `setImmediate` всегда раньше.

## Главное

- Пока стек вызовов не пуст, никакой асинхронный колбэк не выполнится.
- Виток цикла: одна задача, затем все микрозадачи, затем, если пора, кадр с `requestAnimationFrame`.
- Промисы, `await` и `queueMicrotask` это микрозадачи; таймеры и события это задачи.
- Бесконечные микрозадачи вешают страницу; долгие задачи задерживают кадры и ввод.
- Порядок `setTimeout` и `requestAnimationFrame` не гарантирован.
