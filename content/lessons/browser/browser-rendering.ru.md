## О чём урок

«Что происходит, когда вводишь адрес в браузере» классический вопрос собеседования. Здесь фронтендерская половина ответа: как HTML, CSS и JavaScript превращаются в пиксели, что блокирует первую отрисовку и как это ускорить. Сетевая часть (DNS, TLS, HTTP/2 и HTTP/3, кэш) разобрана в треке [«Сеть и HTTP»](/track/network).

## Критический путь рендеринга

Пока HTML приходит по сети, браузер разбирает его **потоком**, не дожидаясь конца файла:

1. **DOM.** Парсер превращает разметку в дерево узлов.
2. **CSSOM.** Каждый найденный стиль (`<link rel="stylesheet">`, `<style>`) разбирается в дерево правил.
3. **Render tree.** DOM и CSSOM объединяются в дерево того, что будет видно: `display: none` и содержимое `<head>` туда не попадают, а `visibility: hidden` попадает (место занято).
4. **Layout** (reflow). Вычисляются размеры и позиции каждого блока.
5. **Paint.** Блоки превращаются в команды рисования: фон, текст, рамки, тени.
6. **Composite.** Слои собираются в кадр, часто на GPU.

Первая отрисовка (FCP) случается, когда браузер получил весь CSS, нужный для первого экрана, и достроил дерево до этого места.

## Что блокирует отрисовку

- **CSS блокирует отрисовку.** Браузер не рисует страницу, пока не загрузит стили из `<head>`, иначе пользователь увидел бы вспышку неоформленного контента. CSS не останавливает разбор HTML, но задерживает выполнение следующих за ним скриптов: скрипт может спросить стили.
- **Обычный `<script>` блокирует парсер.** Разбор HTML останавливается, пока скрипт загружается и выполняется: скрипт может вызвать `document.write` или изменить DOM.

| Тег | Загрузка | Выполнение | Порядок |
|---|---|---|---|
| `<script>` | останавливает парсер | сразу | по порядку |
| `<script defer>` | параллельно | после разбора HTML, до `DOMContentLoaded` | по порядку |
| `<script async>` | параллельно | сразу по загрузке, прерывая парсер | не гарантирован |
| `<script type="module">` | параллельно | как `defer` | по порядку |

Практическое правило: свои скрипты подключают с `defer` или как модули, независимые сторонние (аналитика) с `async`.

## Сканер предзагрузки

Пока основной парсер стоит на скрипте, отдельный **preload scanner** просматривает разметку вперёд и заранее запрашивает картинки, стили и скрипты, которые там видит. Поэтому ресурсы, вставленные из JavaScript (`img.src = …` в коде, стили через `import` в рантайме), загружаются позже, чем те же ресурсы в HTML: сканер их не видит.

Подсказки браузеру:

- `<link rel="preload" href="font.woff2" as="font" crossorigin>`: загрузить важный ресурс, который сканер найдёт поздно (шрифт из CSS, картинка героя из стилей).
- `<link rel="preconnect" href="https://cdn.example.com">`: заранее открыть соединение с другим доменом.
- `fetchpriority="high"` на `<img>` главного изображения: поднять приоритет загрузки для LCP.
- `<img loading="lazy">` для картинок ниже первого экрана; для LCP-картинки ленивая загрузка вредна.

## Как это измеряют сейчас

Метрики FMP (First Meaningful Paint) и TTI (Time to Interactive) из старых статей больше не используются: Lighthouse убрал их, потому что они плохо отражали опыт пользователя. Сейчас смотрят:

- **TTFB**: когда пришёл первый байт ответа;
- **FCP**: первая отрисовка любого контента;
- **LCP**: отрисовка самого крупного элемента первого экрана, хорошо до 2,5 с;
- **CLS**: сдвиги вёрстки, хорошо до 0,1;
- **INP**: задержка реакции на ввод, хорошо до 200 мс.

Подробно о них в треке [«Производительность»](/track/performance). HTTP/2 Server Push, который часто советуют для ускорения, удалён из Chrome; вместо него используют `preload` и ответ `103 Early Hints`.

## Главное

- DOM, CSSOM, render tree, layout, paint, composite; HTML разбирается потоком.
- CSS блокирует отрисовку и выполнение следующих скриптов, обычный скрипт блокирует парсер.
- `defer` и модули выполняются по порядку после разбора, `async` сразу по загрузке.
- Preload scanner загружает ресурсы из разметки заранее; ресурсы из JS он не видит, для них есть `preload`.
- Актуальные метрики: TTFB, FCP, LCP, CLS, INP; FMP, TTI и Server Push устарели.
